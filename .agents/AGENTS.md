# Google Chat TUI 設計書

## 1. 概要

### 1.1 目的

Google Chatをターミナル上から利用できるTUI（Terminal User Interface）アプリケーションを開発する。

Google Chatの主要なコミュニケーション機能をキーボード中心で利用できるようにし、ブラウザを開かずに以下の操作を行えることを目標とする。

- スペース一覧の閲覧
- ダイレクトメッセージ（DM）の閲覧
- メッセージの閲覧
- メッセージの送信
- メッセージの検索
- スペースの切り替え
- メッセージの更新

本プロジェクトでは、Google ChatのWeb UIをそのまま再現するのではなく、**TUIという制約に最適化された独自のUI/UXを設計する**。

---

# 2. 基本方針

## 2.1 UIの基本思想

以下を重視する。

- 情報密度を高くする
- キーボード操作を最優先する
- 不要な枠線を多用しない
- Google Chatの情報構造を参考にする
- ターミナルでも視認性を確保する
- 画面サイズに応じてレイアウトを変更する
- 選択中の項目を明確にする
- API通信中の状態を明確にする
- UIとGoogle Chat APIの処理を分離する

### 2.2 禁止事項

以下のような「典型的な簡易TUI」にならないようにする。

- すべての領域を太いBoxで囲む
- 意味のない枠線を大量に使用する
- 文字色を大量に使用する
- 画面全体を固定レイアウトにする
- マウス操作を前提とする
- キーバインドを画面内で確認できない
- API処理とUIコンポーネントを直接結合する

# 9. メッセージ表示

## 9.1 基本表示

```text
田中  15:32
明日の課題についてです。

佐藤  15:34
了解です！
```

## 9.2 同一ユーザーの連続投稿

```text

資料も確認してください。

15:35
```

ターミナル幅に合わせて自動折り返しする。

横方向のスクロールは基本的に使用しない。

## 9.4 時刻

現在の日付と異なる場合は日付を含める。

例：

```text

```

```text
田中  8/19 15:32
```

# 11. キーバインド

## グローバル

| キー | 動作 |
|---|---|
| `q` | アプリ終了 |
| `Ctrl+C` | 終了 |
| `r` | 現在の画面を更新 |
| `/` | 検索 |
| `?` | ヘルプ |

## サイドバー

| キー | 動作 |
|---|---|
| `↑` / `k` | 上へ |
| `↓` / `j` | 下へ |
| `Enter` | スペースを開く |
| `Esc` | 選択解除/戻る |

## Chat

| キー | 動作 |
|---|---|
| `↑` / `k` | メッセージ上へ |
| `↓` / `j` | メッセージ下へ |
| `PageUp` | 1ページ上へ |
| `PageDown` | 1ページ下へ |
| `Home` | 最上部 |
| `End` | 最新メッセージ |
| `Esc` | サイドバーへ |

## 入力

| キー | 動作 |
|---|---|
| `Ctrl+Enter` | 送信 |
| `Esc` | 入力終了 |
| `↑` / `↓` | 入力履歴（将来実装） |

# 13. Google認証

初回起動時にOAuth認証を行う。

```text
Google Chat TUI

Googleアカウントへのアクセスが必要です。

Enter: ブラウザで認証
Esc: 終了
```

認証用URLをブラウザで開く。

認証完了後、トークンを安全な場所に保存する。

2回目以降は保存済みトークンを利用し、可能な限り再認証を要求しない。

# 14. APIレイヤー

UIからGoogle Chat APIを直接呼び出さない。

例えば、

```ts
interface ChatService {
  listSpaces(): Promise<Space[]>;
  getMessages(spaceId: string): Promise<Message[]>;
  sendMessage(
    spaceId: string,
    text: string
  ): Promise<Message>;
}
```

のようなサービス層を作る。

UIはGoogle APIの具体的な仕様を知らなくても動作できるようにする。

---

# 15. データモデル

アプリ内部ではGoogle APIのレスポンスをそのままUIに渡さない。

アプリ独自の型へ変換する。

```ts
interface Space {
  id: string;
  name: string;
  type: "space" | "dm" | "group_dm";
  unreadCount?: number;
}

interface Message {
  id: string;
  spaceId: string;
  sender: {
    id: string;
    name: string;
  };
  text: string;
  createTime: Date;
}
```

APIの変更によるUIへの影響を最小化する。

# 17. ローディング状態

API通信中にUIを停止させない。

例：

```text
# プログラミング

Loading messages...
```

または、

```text
# プログラミング                     ⟳
```

既存データがある場合は、既存データを表示したままバックグラウンドで更新する。

---

# 18. エラー処理

APIエラーをアプリケーション終了に直結させない。

例：

```text
Unable to load messages.

Authentication may have expired.

[r] Retry
[q] Quit
```

認証エラーの場合は再認証を促す。

ネットワークエラーの場合はリトライ可能にする。

---

# 19. キャッシュ

APIへの不要なリクエストを減らすため、以下をキャッシュ対象とする。

- スペース一覧
- 最近開いたスペースのメッセージ
- ユーザー情報

ただし、キャッシュを正確な最新情報として扱わない。

画面表示時には必要に応じてバックグラウンド更新する。

---

# 20. 未読管理

未読数をサイドバーに表示する。

```text

  # General
  # 開発                  3
> # プログラミング
```

Google Chat APIから取得できる情報を利用する。

アプリ独自の未読状態を作る場合は、Google Chat側の状態と混同しないようにする。

# 22. UIデザイン原則

## 22.1 色

色は装飾目的ではなく情報伝達目的で使用する。

例：

- 選択中：強調
- 未読：強調
- エラー：警告
- 接続中：状態表示

ターミナルのカラースキームを尊重する。

固定色を大量に使用しない。

## 22.2 枠線

枠線は必要最小限にする。

以下のような「箱だらけ」のUIは禁止。

```text
┌────────────┐
│ ┌────────┐ │
│ │        │ │
│ └────────┘ │
└────────────┘
```

空白、文字の配置、区切り線を優先する。

## 22.3 情報密度

画面内に可能な限り多くのメッセージを表示する。

ただし、可読性を犠牲にしない。

---

# 23. アクセシビリティ

以下を考慮する。

- 色だけに依存しない
- Unicode記号が表示できない端末でも最低限利用できる
- マウスなしで全操作可能
- 80 columns程度でも使用可能
- キーバインドを確認できる
- 長文を読みやすく折り返す

---

# 24. セキュリティ

OAuthトークンをソースコードに含めない。

以下をGitへコミットしない。

```text
credentials.json
token.json
.env
```

`.gitignore`に追加する。

また、ログにアクセストークンやユーザーのメッセージ本文を出力しない。

# 28. AIエージェントへの実装指示

本プロジェクトでは、機能実装よりも**UI/UXの品質を優先する**。

特に以下を厳守する。

1. 最初からGoogle Chat APIを実装せず、Phase 1ではモックデータでUIを完成させる。
2. 「TUIだから」という理由で簡素なBoxレイアウトにしない。
3. Google Chatの情報構造を参考にする。
4. UIは余白・文字の強弱・選択状態を利用して情報を整理する。
5. 枠線は必要最小限にする。
6. キーボード操作を最優先する。
7. ターミナルの横幅が変化してもレイアウトが破綻しないようにする。
8. API層とUI層を完全に分離する。
9. Google APIのレスポンスをUIコンポーネントへ直接渡さない。
10. 仮実装・ダミーデータを残したまま完成扱いにしない。
11. エラー・ローディング・空状態をUI設計段階から考慮する。
12. UIを実装したら、最低でも広い画面・80 columns程度・狭い画面の3パターンで確認する。

最終的な目標は「Google Chatをターミナルに移植すること」ではなく、**Google Chatの操作性をTUIという環境に合わせて再設計し、実用的なGoogle Chatクライアントを作ること**である。
